# Обязательный Git-процесс проекта

Этот порядок работы обязателен для каждой задачи в проекте.

## Начало новой задачи

1. Новая задача начинается только от актуальной и чистой ветки `main`.
2. Перед началом работы необходимо синхронизировать локальный `main` с удалённым репозиторием.
3. Для каждой новой задачи создаётся отдельная рабочая ветка от `main` с именем вида `work/<название-задачи>`.
4. Нельзя начинать новую задачу непосредственно в `main` или продолжать её в ветке предыдущей задачи.

## Завершение задачи

1. Проверить выполненную работу и состояние репозитория.
2. Зафиксировать изменения коммитом в рабочей ветке.
3. Отправить рабочую ветку на GitHub командой `push`.
4. После `push` остановиться и сообщить пользователю, что ветка готова к проверке и объединению.

## Pull Request и Merge

1. Pull Request создаёт пользователь самостоятельно.
2. Merge выполняет пользователь самостоятельно.
3. Агенту запрещено создавать Pull Request или выполнять Merge без отдельного прямого запроса пользователя.
4. До сообщения пользователя об успешном Merge агент не синхронизирует завершённую работу с `main` и не начинает следующую задачу.

## Действия после подтверждения Merge

После того как пользователь сообщил, что Merge выполнен, необходимо:

1. Переключиться на `main`.
2. Получить актуальное состояние удалённого репозитория.
3. Обновить локальный `main` безопасным fast-forward обновлением.
4. Убедиться, что локальный `main` совпадает с удалённым и рабочее дерево чистое.
5. Удалить завершённую локальную рабочую ветку.
6. Остаться на чистой и актуальной ветке `main`.

Удаление удалённой рабочей ветки выполняет пользователь на GitHub, если он считает это необходимым.

## Следующая задача

Следующая задача начинается только после подтверждённого Merge, синхронизации `main` и создания новой рабочей ветки от актуального `main`.

# Обязательное журналирование обсуждений

Для каждой самостоятельной задачи ведётся отдельный журнал в каталоге
`docs/discussions/`. Имя файла начинается с идентификатора Work Plan, например:
`docs/discussions/WP-003-telegram-ingestion-bot.md`.

## Распределение информации

- `WORK_PLANS.md` хранит перечень работ, их статус, ветку и ссылку на журнал.
- `docs/discussions/<задача>.md` хранит анализ, вопросы, решения, согласованное
  задание, разрешение на реализацию и результаты проверки.
- `CHANGELOG.md` хранит только существенные фактически выполненные изменения.
- Дословная стенограмма разговора в репозиторий не переносится.
- Секреты, токены, пароли и лишние персональные данные в журнал не записываются.

## Порядок заполнения журнала

1. Во время Фаз 1 и 2 изменения файлов запрещены, поэтому обсуждение сначала
   остаётся в диалоге.
2. После рекомендации модели и явного разрешения пользователя на Фазу 3 агент
   синхронизирует `main` и создаёт отдельную рабочую ветку.
3. Первым содержательным изменением в ветке агент создаёт или обновляет журнал и
   переносит в него существенные результаты Фаз 1 и 2.
4. Каждый существенный вопрос получает идентификатор `Q-001`, `Q-002` и далее,
   статус `открыт`, `решён` или `отложен`, а после решения — краткий ответ.
5. До реализации в журнале фиксируются согласованное задание, выбранная модель,
   уровень рассуждения и явное подтверждение пользователя.
6. В ходе Фазы 3 журнал дополняется кратким перечнем реализации и проверок.
7. Перед коммитом журнал не должен содержать открытых вопросов, блокирующих
   выполненную реализацию. Отложенные вопросы получают понятную точку возврата.

Используется шаблон `docs/discussions/TEMPLATE.md`.

## Возобновление работы

Проектная команда `/resume <WP-ID>` означает просьбу продолжить указанную работу.
Это соглашение проекта, а не встроенная команда Codex.

Получив такую команду, агент должен:

1. Прочитать `AGENTS.md`, `WORK_PLANS.md` и журнал указанной работы.
2. Кратко восстановить принятые решения и текущую фазу.
3. Показать оставшиеся открытые или отложенные вопросы.
4. Продолжить с первой незавершённой точки, соблюдая фазовый порядок.

Команда `/resume` сама по себе не является разрешением на Фазу 3 и не отменяет
требование отдельного явного подтверждения реализации.
